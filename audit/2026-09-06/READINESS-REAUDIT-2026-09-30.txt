B. IMPLEMENTATION AND NEW WORK

Web: Next.js App Router, API handlers, cookie/Bearer authentication, privileged
Supabase server access. Mobile: Expo/React Native, mobileApiClient and direct
Supabase auth/session integration. PostgreSQL migrations contain transactional
payment, retention and property rules; Storage holds private evidence. Stripe
webhook handlers and reconciliation coordinate payment state. Notification queues
and cron routes provide background work. AI assessment has schema/error handling
and a human review form; passing mocks establish no model-accuracy claim.

Property management now adds paginated report conversations to manager report
screens and mobile portfolio/job screens. Residents receive a random private
receipt link; only its hash is stored. Managers and the currently assigned
contractor are checked against database records. Message insertion and queued
notifications are atomic. Stable message IDs reject changed retry payloads.
Report status changes create system history entries. Receipt links are bearer
capabilities: anyone given the link can read/write that report. Do not share them.
Residents refresh the receipt page; outbound resident email is not implemented.

Visit confirmations appear on the web Visit confirmations page and mobile
calendar. Client identity and exact date/start/end are verified under a row lock.
Rescheduling resets confirmation; direct client-role writes cannot forge it.
Existing appointments lacking an explicit client_id are visible through legacy
list matching but intentionally cannot be confirmed on someone else's behalf.
New workflows still require current-release browser/device acceptance.

C. PRIORITISED FINDINGS

R1 — High impact, high confidence; web export falsely succeeded after read errors.
FIXED IN THIS CHANGE, not yet verified in a deployed release.
apps/web/app/api/user/export-data/route.ts, POST: profile/property/job/message
reads and secondary category reads previously discarded errors and used empty
arrays. The active caller is app/settings/_components/settings-api.ts:162.
A database outage on contracts/payments could yield HTTP 200 and an apparently
complete download. The route now rejects any failed requested category; seven
tests cover six failed categories and successful export. Mobile's distinct
api/gdpr/export-data route already rejects failed secondary categories, despite
an obsolete best-effort comment. Do not report both routes as having this defect.
Acceptance: deployed web shows a retryable error and offers no completed export
when any required read fails.

R2 — Medium impact, high confidence; export completeness beyond row limits and
new/retained categories remains unresolved.
apps/web/app/api/user/export-data/route.ts, POST reads use unpaginated select;
api/gdpr/export-data/route.ts also has unpaginated supplemental category reads.
Neither inspected export assembles the new report_messages or the retained
dispute archive. A large account can reach the backend row cap; a user expecting
all conversation/retained evidence will not receive it from these code paths.
This is distinct from the already fixed retained-record LIST pagination.
Fix: shared, bounded paginated export service with explicit inclusion/access
rules and a manifest of categories and file availability. Test more than one
backend page, all participant roles and failed middle-page recovery. Closed
accounts need an authenticated operator-assisted access/export path; an archived
record list for a still-signed-in participant is not sufficient proof.

R3 — Release blocker, high confidence in missing evidence; backup/recovery.
A separate encrypted backup approach was requested, but this run establishes no
configured destination, successful scheduled backup or restoration exercise.
No amount of local emulator/cache cleanup supplies production disaster recovery.
Before public use: select destination, configure limited credentials/encryption,
produce and restore database plus required storage evidence into isolation,
measure recovery, test expiry and restoration-time deletion suppression.
This is an operational gap, not a claim that the database has already lost data.

R4 — Retention operating gap, high confidence; external evidence disposal.
supabase/migrations/20260924084212_add_retained_evidence_disposal_queue.sql:133
explicitly routes external evidence to reconciliation. api/cron/evidence-disposal
returns a failure when reconciliation remains, rather than falsely reporting
deletion. That is a useful safeguard, but not proof that files are actually
disposed of. lib/properties/cleanup-document-files.ts separately deletes orphaned
property documents in batches through Storage, then removes their database row.
Acceptance: synthetic external-file disposal including provider-success/DB-failure,
legal hold, retry, missing object, backup expiry and restored deleted record.
Do not clear reconciliation merely by removing database storage metadata.

R5 — Security hardening and release maintenance, advisor-confirmed configuration.
Hosted advisor still reports leaked-password protection disabled and available
Postgres security updates. It also flags spatial_ref_sys RLS, public PostGIS and
callable SECURITY DEFINER helpers. These are not all exploitable vulnerabilities.
Reviewed has_org_management_access and is_org_member bind supplied user IDs to
auth.uid; is_admin(uuid) does likewise; is_job_participant checks current identity.
RLS-without-policy on service-only tables is fail-closed, not a permission leak.
Remaining helpers/grants need individual caller and search_path review. Enable
supported password protection and plan the supported DB update with backup and
restore evidence. Never weaken RLS merely to remove an advisor warning.
