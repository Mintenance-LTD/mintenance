Prioritized findings

P1 · RELEASE BLOCKER · LIVE DATABASE VERIFIED

1. Authenticated users can read other users’ private profile contact fields

The live profiles_select policy allows every authenticated caller to select any non-deleted profile. Column privileges also grant access to email, phone, address, postcode, coordinates, settings and notification preferences. This exposes more than the public contractor directory needs, including homeowner and administrator profiles.

A read-only transaction assumed the authenticated database role with an unrelated synthetic subject. It could count 11 other profiles, 11 readable emails, 7 readable phone numbers and 4 readable addresses. No personal field values were retrieved. This tests database authorization, not token forgery.

Fix: separate public contractor-directory fields from private account data, enforce owner/admin access to the latter, and add two-user direct Data API tests for homeowners, contractors and admins. A server-side response filter alone does not close direct Supabase access.

Sources: baseline migration, policy at line 33798; email/phone/address grants at 37460, 37479, 37483. Reproduction SQL.

P1 · RELEASE BLOCKER · LIVE FAILURES CONFIRMED

2. Data retention is configured but fails in production

Over the observed seven days, pii-cleanup failed 7 times, retention-cleanup failed 4 times and data-archival failed once. Vercel logs independently confirm the first two failures.

  • pii-cleanup writes and compares 'anonymized' against security_events.ip_address, an inet NOT NULL column. PostgreSQL rejects the value.
  • run_retention_cleanup and archive_old_records do not exist in the live public schema. Their scheduled callers cannot succeed.

Fix: implement a schema-compatible anonymization strategy and the missing retention/archive operations with appropriate evidence-retention exclusions. Verify them on realistic disposable records, then observe successful scheduled runs and alert delivery. The PII job partially succeeds in other categories; it is specifically the security-event anonymization that fails.

Sources: PII cleanup lines 43–45; retention line 18; archival line 17. Database checks.

P1 · RELEASE GATE FAILED

3. Dependency security exceptions no longer cover the current tree

The configured security gate fails. Locked versions include Axios 1.18.1, gRPC 1.14.3, ws 8.20.1 and node-forge 1.4.0. Newly unaccepted high advisories include Axios, gRPC, braces and node-forge. Existing exceptions also retain older advisories.

The 62 high entries are affected packages, including inherited transitive findings—not 62 independently exploitable application vulnerabilities. Expo/build tooling also appears in the production-classified monorepo dependency graph. Runtime reachability requires triage.

Fix: update compatible affected dependencies, identify which remaining findings reach server or shipped mobile runtime, and document narrow time-bounded exceptions only where justified. Re-run the existing gate and regression tests. Axios’s upstream advisory identifies a fix in 1.20.0 and describes configuration-dependent impact; an application exploit was not attempted.

Sources: fresh audit, gate result, exception configuration, Axios advisory, gRPC advisory.

P1 · MOBILE SIGN-OFF BLOCKED

4. Mobile regression evidence is not green

The current working copy has 11 failing mobile suites. Failures include missing Expo native-module mocks (EventEmitter, through file-system/encryption code), a missing navigation.replace mock in job creation, and profile/map/job-card assertions. Re-running three representative files serially reproduces their failures.

These are test failures, not confirmation that all those screens crash on devices. However, the suite currently cannot certify the edited navigation and onboarding paths. Some affected files are uncommitted.

Fix: repair the test harness and investigate behavioral assertions; freeze a release commit; then test the actual release APK and iOS build on devices, including session restoration, permissions, offline recovery, navigation/back behavior, camera uploads and notification deep links.

Sources: full results and serial reproduction. No emulator or physical-device validation was performed in this audit.

P2 · CONFIRMED PUBLIC ROUTING MISMATCH

5. Public handler declarations disagree with the outer authentication layer

/api/health, /api/version, /api/contact and /api/ai/search-suggestions are declared public by handlers but absent from the public-route allowlist. Unauthenticated GET probes returned 401. The public contact form posts to the same blocked contact path, so its anonymous workflow is inconsistent with its advertised availability. No message was submitted.

Fix: explicitly align each intended public route in the outer layer while retaining validation, rate limits and CSRF where appropriate. Add deployed anonymous browser/API tests. Do not whitelist the entire API.

Sources: public-route classification line 50 onward; contact form line 191; health/version HTTP checks.

P2 · OPERATIONAL DETECTION GAP

6. The Redis health probe can mistake fallback behavior for a healthy dependency

The health route uses rateLimiter.checkRateLimit() as a Redis probe and marks it healthy based on elapsed time. The limiter catches Redis failures and returns an in-memory fallback result. A quick Redis failure can therefore appear healthy, while critical login/payment/admin requests deliberately fail closed.

Fix: use an explicit bounded Redis check or expose the limiter’s backend/degraded state. Monitor a login/payment canary and recovery queues alongside infrastructure probes.

Code review finding, not an induced production outage. Sources: health route lines 105–124 and rate limiter lines 164–200.

P2 · DATABASE MAINTENANCE

7. Hosted database patches and access-policy cleanup remain

Supabase reports outstanding security patches for Postgres image 17.4.1.074 and disabled leaked-password protection. Plan a supported upgrade with compatibility checks and recovery verification before broader beta exposure.

Of 379 public tables, 377 have RLS enabled. The two exceptions are PostGIS spatial_ref_sys and contractor_payout_credit_events; the latter has access revoked from anon/authenticated and is not a confirmed public exposure. Its missing RLS is defense-in-depth debt. The 82 “RLS enabled, no policy” notices are largely backend-only tables and are not automatically security holes.

Flagged privileged membership helpers checked in this audit bind their user argument to auth.uid(). Do not blindly remove helper permissions needed by policies. Performance advisors also report 26 unindexed foreign keys, one duplicate service-area index and 828 unused-index notices; low traffic can explain unused indexes, so mass deletion is unwarranted.

Sources: advisor evidence; database upgrade guidance; password protection; foreign-key indexing.

P1 · VALIDATION GAP BEFORE RELEASE

8. The available test environments do not match the hosted schema

The hosted migration history has 384 entries through 30 September. The root Docker database has 301 through 31 August; the separate audit stack has 310 through 7 September. The local schema comparison completes with substantial differences, including newer recovery tables absent locally. Generated DROP statements describe migration-baseline versus stale-local differences; they are not a repair to apply.

The named hosted staging project is currently inactive. Existing web unit tests mock Supabase, and the real-database suites are explicitly excluded from the default run. Passing 4,345 web tests therefore does not establish current database integration correctness.

Fix: provision a disposable environment from the release migration set, run the existing real-database isolation/payment/contract suites there, and execute the complete two-sided customer journey against Stripe test mode. Verify backup restoration and alert delivery as separate release checks.

Sources: migration evidence, local comparison, default test configuration, real-database configuration.

Concrete release gates

  1. Close cross-user profile access. A homeowner and contractor must be unable to retrieve another account’s private fields through direct Supabase access; directory lookup must still work using only approved public fields.
  2. Make retention work. Repair all three jobs, validate data/evidence exceptions on fixtures, and observe successful scheduled executions with a tested failure alert.
  3. Restore a green release gate. Resolve or explicitly justify the remaining dependency findings; fix mobile failures; repeat checks on a frozen release commit.
  4. Create a matching test environment. Apply the 384-migration baseline to a disposable database and run real-database isolation, bid acceptance, contracts, payment lifecycle and recovery tests.
  5. Prove the actual beta journey. Register/verify/reset password; create a property and job; discover/bid/accept; sign; pay in test mode; message/upload; complete/release; refund/dispute; revoke sessions/delete account. Include webhook retries, duplicate taps and provider timeouts.
  6. Verify the distributed builds. Run Android/iOS device checks and deploy checks against the exact release; confirm public contact access, external monitoring, support routing and restore capability.

Recommended beta shape after these gates: an invitation-only cohort with a tightly defined homeowner/contractor journey, monitored support, limited optional features and Stripe test-mode validation first. Broader access or real-money use needs its own verified payment and operational acceptance. Today, internal testing with synthetic data is appropriate; inviting unrelated users with real personal data is not.
